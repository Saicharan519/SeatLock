# Security review (2026-11-10, start of Phase 16)

SeatLock was built with an AI coding assistant. Reports on AI-built ("vibe-coded") apps keep finding the same problems: secrets shipped to the browser or committed to git, server endpoints that don't check who is asking, open defaults, missing rate limits, and logs that leak data. This review checked SeatLock against that list, **by testing, not by reading alone**, before the hardening phase.

Sources for the checklist: [Escape.tech's scan of 5,600 vibe-coded apps](https://escape.tech/blog/methodology-how-we-discovered-vulnerabilities-apps-built-with-vibe-coding/), [Wiz on the Moltbook leak](https://www.wiz.io/blog/exposed-moltbook-database-reveals-millions-of-api-keys), [Invicti's checklist](https://www.invicti.com/blog/web-security/vibe-coding-security-checklist-how-to-secure-ai-generated-apps), [Nurbak's checklist](https://nurbak.com/en/blog/vibe-coding-security/), [Cycode](https://cycode.com/blog/vibe-coding-security/), [a scan of 978 apps for keys in the frontend](https://dev.to/sandeep_roy_c4e518c3f2641/i-scanned-978-vibe-coded-apps-1-in-26-ships-a-secret-api-key-to-every-visitor-2nj1).

## The Content-Security-Policy, and how it was tested

```
default-src 'self'; script-src 'self' https://sdk.cashfree.com;
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com;
img-src 'self' data: https:; connect-src 'self' https://*.cashfree.com; frame-src https://*.cashfree.com;
form-action 'self' https://*.cashfree.com; frame-ancestors 'none'; base-uri 'self'; object-src 'none'
```

- Scripts only from the site itself and Cashfree's checkout SDK (which Cashfree requires to load from its CDN). The build has no inline scripts.
- Images from any HTTPS host, because admins can set any poster URL.
- `frame-ancestors 'none'`: no other site can frame SeatLock (clickjacking).
- `form-action` allows Cashfree: the SDK reaches the hosted checkout with a form POST.

A too-strict policy silently breaks pages, so the policy lives in one place (`frontend/vercel.json`) and `npm run preview` serves the production build with exactly those headers (read from the same file). Under it: home, posters, fonts, the seat map, checkout, and a real Cashfree sandbox checkout all worked, with no violations in the console.

## Found on the way

Testing the Cashfree checkout under the new policy exposed a Phase 14 bug: on "Finish your payment", the **Release seats** button could never work. With a payment open at Cashfree the API refuses a release (the customer could still pay), so the button only produced an error. It's replaced by a line saying the seats are released when the timer runs out.

## Still true (known limitations)

- The JWT is in `localStorage`, readable by any script that runs on the page. The CSP now makes injecting such a script much harder; moving the token to an httpOnly cookie removes the exposure. That's the next step of Phase 16.
- No account lockout beyond the per-IP rate limit; no password reset (no email in this project).
- Registration says when an email is already taken (account enumeration), traded for a clear sign-up error.

# Decisions and trade-offs

Every place the implementation deviates from, or fills a gap in, the PRD, with the reason. The PRD's own decisions log (section 15) still applies; this file records what was decided while building.

Format: **Decision**, then the rejected alternative, then why.

## A. Design decisions from the PRD review (v1.1 → v1.2)

Made before coding, after two independent reviews of the PRD.

| #   | Decision                                                                                                                             | Rejected                                      | Why                                                                                                                                                                                 |
| --- | ------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | The hold builds **one lock set** (requested seats + the caller's stale hold's seats), locks it in id order, then releases and claims | Releasing the stale seats in a separate pass  | Two passes can lock seats out of id order, recreating the deadlock cycle R2 exists to prevent. Example: X holds stale {5, 9}, requests {1, 5}; Y holds 1 and wants 9                |
| A2  | Plain blocking `FOR UPDATE` on seats                                                                                                 | `NOWAIT` / `SKIP LOCKED` on seats             | With `NOWAIT`, a multi-seat loser could be told "unavailable" about a seat whose holder later rolled back. Wrong answers under contention                                           |
| A3  | Generous pool **acquire** timeout; T1 must produce zero 503s                                                                         | Short timeout                                 | 1,000 requests queue for 20 connections; a short acquire timeout turns correct 409s into pool errors                                                                                |
| A4  | `UNIQUE (user_id, key)` on idempotency keys                                                                                          | `UNIQUE (user_id, key, endpoint)`             | The request hash includes the path, so reusing a key on another endpoint is correctly a 422 instead of silently allowed                                                             |
| A5  | **Lock → verify → update** for confirmations and the late path                                                                       | Savepoints                                    | With the rows locked nothing can change between the check and the update, so it's all-or-nothing by construction                                                                    |
| A6  | Insert the booking **before** claiming seats                                                                                         | Claim seats first                             | Booking-first lets the `one_pending_per_user_show` index fail fast, and avoids a deferred foreign key on `seats.booking_id`. The saving (~950 rolled-back inserts in T1) is trivial |
| A7  | Crash between the pay commit and the gateway call is a **documented limitation**                                                     | A worker job that re-drives orphaned payments | Small impact: the hold expires in 5 minutes and the sweep fails the payment. Not worth the code                                                                                     |
| A8  | Re-verify the stale booking **after** locking (implemented via `FOR UPDATE`, which re-checks `status = 'PENDING'`)                   | Trusting the unlocked read                    | The worker or a webhook may change it between the read and the lock                                                                                                                 |
| A9  | Phases are vertical slices, expiry worker early                                                                                      | The PRD's original weekly order               | Something demoable exists from Phase 3 on                                                                                                                                           |

## B. Stack and project setup

| #   | Decision                                                                                                          | Rejected                    | Why                                                                                                                           |
| --- | ----------------------------------------------------------------------------------------------------------------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| B1  | **Node 24 LTS**                                                                                                   | Node 20 (in the PRD)        | Node 20 reached end-of-life in April 2026. Shipping on an EOL runtime is a red flag                                           |
| B2  | **One package**, three entry points, shared code via TypeScript path aliases (`@seatlock/db`, `@seatlock/shared`) | npm workspaces              | Simpler. The PRD calls for a modular monolith in one repo; workspaces add tooling for no benefit here                         |
| B3  | Run TypeScript with **`tsx`**, typecheck with `tsc --noEmit`                                                      | Compile to `dist/`          | No build step, no path-alias rewriting. Trade-off: slightly slower startup; may add a build for production images in Phase 10 |
| B4  | Postgres on host **port 5433**                                                                                    | 5432                        | A local Postgres on this machine already uses 5432. Inside Docker it is still 5432                                            |
| B5  | **Express 5**                                                                                                     | Express 4                   | Errors thrown in async handlers reach the error handler automatically                                                         |
| B6  | **`bcryptjs`** (pure JS)                                                                                          | `bcrypt` (native)           | No native compilation on Windows or Alpine. Same algorithm and hash format; slower, irrelevant at this scale                  |
| B7  | Statuses as **`text` + `CHECK`**                                                                                  | Postgres `ENUM`             | Adding a state is a one-line migration                                                                                        |
| B8  | **SQL migrations** (node-pg-migrate)                                                                              | JS/TS migrations            | The schema is plain SQL anyone can read; matches the no-ORM stance                                                            |
| B9  | Accept a **moderate `npm audit`** finding in node-pg-migrate's glob dependency                                    | Downgrading the tool        | It only runs during migrations, never in the request path                                                                     |
| B10 | Extra pool setting `idle_in_transaction_session_timeout = 10s`                                                    | Only the PRD's two timeouts | A bug that leaves a transaction open can't hold locks forever                                                                 |

## C. API behaviour (gaps the PRD left open)

| #   | Decision                                                                                                                              | Why                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| C1  | New error code **`EMAIL_TAKEN` (409)** for duplicate registration                                                                     | The PRD's error table had no code for it                                                    |
| C2  | Login returns the **same error and takes the same time** for a wrong password and an unknown email (bcrypt runs against a dummy hash) | Prevents discovering which emails are registered                                            |
| C3  | Emails are **lowercased** before storage                                                                                              | One account per address regardless of case                                                  |
| C4  | Malformed UUIDs in URLs return **404**, not 400                                                                                       | A malformed id can't exist; same answer as unknown                                          |
| C5  | Someone else's booking returns **404**, not 403                                                                                       | Doesn't reveal that the booking exists                                                      |
| C6  | The **role is inside the JWT**                                                                                                        | No DB lookup per request. Trade-off: a role change needs a fresh login (tokens last 1 hour) |
| C7  | Only **HS256** accepted when verifying JWTs                                                                                           | Blocks algorithm-confusion attacks                                                          |
| C8  | Seat labels validated as `^[A-Z][1-9]\d?$`, case-insensitive, then checked against the show                                           | Bad input rejected at the edge; unknown labels are a 400 naming them                        |
| C9  | Idempotency hash uses the **parsed body with seats sorted**                                                                           | `["A2","A1"]` and `["A1","A2"]` are the same request                                        |
| C10 | Replayed responses carry an **`Idempotent-Replayed: true`** header                                                                    | Clients and tests can tell a replay from a fresh execution                                  |
| C11 | A second pay attempt with a new key returns **`PAYMENT_IN_PROGRESS` (409)**                                                           | One payment per booking; the PRD defined this code only for release                         |
| C12 | Releasing an already-CANCELLED hold returns **200** with the current state                                                            | Naturally idempotent, like cancellation                                                     |
| C13 | Releasing a PENDING hold that is past expiry is **allowed** (→ CANCELLED)                                                             | Harmless and simpler than a special case                                                    |
| C14 | Lock timeout (`55P03`) is **retried** like deadlocks                                                                                  | The PRD's error table maps lock-timeout exhaustion to 503 RETRY_LATER                       |
| C15 | Cancel returns `{ bookingId, status, refund: { paymentId } }`                                                                         | The client can track the refund                                                             |

## D. Payments and webhooks

| #   | Decision                                                                                                                                      | Why                                                                                                                      |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| D1  | Signature header **`X-SeatLock-Signature: t=<unix>,v1=<hex>`**, HMAC over `"<t>.<raw body>"`                                                  | Same scheme as Stripe; the timestamp is signed so it can't be swapped                                                    |
| D2  | Timestamp tolerance **±5 minutes** (past and future)                                                                                          | Blocks replays and tolerates small clock skew                                                                            |
| D3  | Webhook route mounted **before** the JSON parser, reading the raw Buffer                                                                      | Re-serialised JSON may not match the signed bytes                                                                        |
| D4  | **Unknown payment** or **amount mismatch** → `200` with result `ignored`, logged as an error                                                  | A non-2xx makes the gateway retry forever; these can never succeed. They need a human, not retries                       |
| D5  | Webhook dedupe stores the raw payload text in `webhook_events`                                                                                | Audit trail of exactly what the gateway sent                                                                             |
| D6  | Outbox events written **from Phase 4** onward                                                                                                 | Events are part of the state change, even before anything delivers them                                                  |
| D7  | Late-path claimable seats include seats **still held by the same booking**, even if live                                                      | Covers the rare fall-through from the in-time path                                                                       |
| D8  | Webhook results are explicit strings (`confirmed`, `confirmed_late`, `refund_required`, `payment_failed`, `refunded`, `duplicate`, `ignored`) | Logged and returned, so every outcome is visible                                                                         |
| D9  | The stuck-payment sweep changes **only the payment**, not the booking                                                                         | The hold expired long ago and the expiry job owns bookings. Also keeps the sweep out of the booking → payment lock order |
| D10 | The mock gateway adds a **`reject`** mode (402) to the PRD's list                                                                             | Needed to test definite rejection (T7)                                                                                   |
| D11 | **T7 and T18 implemented in Phase 4**, not Phase 5                                                                                            | Interpreting the gateway's answer is part of the pay flow itself                                                         |

## E. Testing

| #   | Decision                                                                                                                         | Why                                                                                                                                  |
| --- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| E1  | Tests use a **real Postgres** (separate `seatlock_test` database), never mocks                                                   | Locks, constraints and races can't be mocked meaningfully                                                                            |
| E2  | Test files run **one at a time** (`--runInBand`); tables truncated before each test                                              | They share one database                                                                                                              |
| E3  | **T1 runs with the production TTL (300 s)**; the 5 s test TTL is for expiry tests                                                | On this machine the 1,000-request burst takes > 5 s; with a 5 s TTL late requests legitimately take over expired holds (see results) |
| E4  | Concurrency tests send requests over a **200-socket keep-alive pool**; the server's listen backlog is raised                     | Desktop Windows refuses connections beyond a ~200-deep accept queue. All 1,000 requests are still fired at once                      |
| E5  | T2 uses a **seeded PRNG** and checks Postgres's **`pg_stat_database.deadlocks`** counter                                         | Reproducible failures, and direct proof that R2 prevents deadlocks                                                                   |
| E6  | T14 uses **forced interleaving** (a paused transaction holding a lock, verified via `pg_stat_activity`) plus 20 randomized races | Proves specific orderings instead of hoping a random run hits them                                                                   |
| E7  | Database reset **retries on deadlock**; pending gateway webhooks cancelled between tests                                         | Async webhooks from one test can land in the next                                                                                    |
| E8  | **`TEST_LOG_LEVEL`** env switch shows server logs in tests                                                                       | Tests are silent by default; this found the T14 500                                                                                  |
| E9  | Test webhook events use a **charge id derived from the payment id**                                                              | `payments.provider_reference` is unique; a shared fake id caused false failures                                                      |
| E10 | T11 **kills a real separate worker process with `SIGKILL`** after its side effect                                                | A simulated crash in the same process would not prove recovery from a real process death                                             |
| E11 | Mock gateway counts **refund calls per payment**; tests assert per payment                                                       | Its in-memory state is shared across tests in a file, so global counts mislead                                                       |
| E12 | The T11 worker is started with **`node --import tsx`**, not the `tsx` CLI, and the test asserts the killed pid is gone           | The CLI is a launcher that runs the script in a second process; killing it orphaned the real worker and hung Jest on Linux           |
| E13 | CI job **`timeout-minutes: 15`**                                                                                                 | A hung test fails fast instead of running to GitHub's 6-hour default                                                                 |
| E14 | Platform-sensitive changes are verified by running the suite **on Linux in a Docker container** before pushing                   | Windows hid the orphan-process bug; Linux is what CI and production run                                                              |

## F. Outbox (Phase 6)

| #   | Decision                                                                                | Rejected                                                     | Why                                                                                                                                                                    |
| --- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F1  | **Lease** (claim and commit, run outside a transaction, record in a second transaction) | Holding a row lock across the handler                        | No transaction open during an external call: no long lock, no tied-up connection. Crashed workers are recovered by lease expiry (PRD R7, 9.5)                          |
| F2  | A **fencing token** (`lease_token`, new random UUID per claim) guards result recording  | Guarding only on `status = 'PROCESSING'` (the PRD's wording) | A re-claim also leaves the status PROCESSING, so a slow worker whose lease expired could overwrite the newer worker's result. The token makes the stale update a no-op |
| F3  | Re-claiming an expired lease **counts as a failed attempt**                             | Not counting it                                              | An event whose handler crashes the process would otherwise loop forever. After 8 attempts it goes to FAILED without running                                            |
| F4  | **Batches of 20, handlers run concurrently**                                            | Large batches run one by one                                 | The batch finishes within one handler timeout (10 s), far inside the lease (60 s). A long sequential batch could outlive its own lease                                 |
| F5  | The worker **refuses to start** if `OUTBOX_LEASE_SECONDS` ≤ handler timeout             | Trusting configuration                                       | A lease shorter than the handler lets a healthy, slow handler's event be re-claimed                                                                                    |
| F6  | **One attempt per event per tick**; a tick stops when a claim returns a short batch     | Retrying within the tick                                     | No hot retry loop; backoff and the tick interval pace retries                                                                                                          |
| F7  | Backoff = `base × 2^(attempt−1)`, base 1 s, **capped at 5 minutes**, 8 attempts         | Fixed delay                                                  | Transient outages get several quick retries; long ones don't get hammered. 8 attempts span about 4 minutes before FAILED                                               |
| F8  | Notifications are **rows in `notifications`**                                           | Real email/SMS                                               | Real messaging is a PRD non-goal; the row is the side effect and is idempotent via `UNIQUE(event_id)`                                                                  |
| F9  | The **gateway client lives in the shared package**                                      | A copy per app                                               | The API charges and the worker refunds with the same client                                                                                                            |
| F10 | The outbox is processed on the worker's normal **5-second tick**                        | `LISTEN/NOTIFY` for instant pickup                           | Simpler; up to 5 s of notification latency is acceptable. A possible later improvement                                                                                 |

## G. Hardening (Phase 7)

| #   | Decision                                                                                                | Rejected                             | Why                                                                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| G1  | **Fixed-window** counters in Redis                                                                      | Sliding window / token bucket        | Simple and explainable; abuse protection doesn't need precision. Trade-off: up to 2× the limit across a window boundary                   |
| G2  | Increment and expiry in **one Lua script**                                                              | INCR then EXPIRE as two commands     | Two commands can interleave so a counter never gets an expiry and blocks a client forever                                                 |
| G3  | Holds and pay **share one** per-user bucket (30/min)                                                    | Separate buckets                     | Matches the PRD's "holds and pay 30 req/min per user"; one booking flow, one budget                                                       |
| G4  | Auth limited **per IP**; `TRUST_PROXY` off by default                                                   | Always trusting `X-Forwarded-For`    | Behind a proxy every request shares the proxy's IP, but trusting the header without a proxy lets clients fake their IP                    |
| G5  | **Fail open** on any Redis error                                                                        | Fail closed                          | Redis only protects Postgres; failing closed turns a Redis outage into a full outage (PRD 6)                                              |
| G6  | Redis client: **no offline queue, 0 retries per request, 250 ms command timeout**, background reconnect | Library defaults                     | Defaults queue commands while disconnected, so requests would hang instead of failing open                                                |
| G7  | Health: database down **503**, Redis down **200 degraded**                                              | 503 for any dependency               | A load balancer would pull healthy instances out of rotation during a Redis outage the API survives                                       |
| G8  | Transitions logged **after commit** via an `afterCommit` hook in the transaction helper                 | Logging at the UPDATE                | Rolled-back transitions (failed holds, deadlock retries) would appear in the logs as if they happened                                     |
| G9  | Logging hooks into the **two guarded-transition functions**                                             | Logging at each call site            | Every booking and payment transition is covered in one place                                                                              |
| G10 | **`POST /admin/outbox-events/:id/retry`**, beyond the PRD                                               | Inspect-only, fix with SQL           | A guarded FAILED → PENDING with a fresh attempt budget is safer than hand-written SQL; `last_error` is kept as history                    |
| G11 | Rate-limit tests use **Redis database 1**, flushed per test; CI gets a Redis service                    | Sharing database 0                   | Tests never touch dev data                                                                                                                |
| G12 | The health test uses a **stub** for "Redis down"; real unreachable clients only mid-file in T13         | A real unreachable client everywhere | ioredis keeps the process alive ~2.3 s after a refused connection (measured), which delays Jest's exit if it happens at the end of a file |

| --- | -------------------------------------------------------------------------------------- | ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| H1  | **k6 from the `grafana/k6` Docker image**                                              | Installing k6 on the host                         | Reproducible, nothing to install, same version everywhere                                                                           |
| H2  | **API, k6 and Postgres on one Docker network** for load tests                          | API on Windows, k6 calling `localhost`            | Keeps the Windows network stack (and its ~200-deep accept queue) out of the measurement                                             |

| H4  | **1,000 JWTs pre-generated** by a setup script                                         | Logging in during the test                        | PRD 13; keeps bcrypt and login out of the hold measurement                                                                          |
| H5  | **Rate limiting disabled** for load runs, and stated in the results                    | Leaving it on                                     | Otherwise the limiter's 429s would be measured instead of the system                                                                |
| H6  | k6 treats **201 and 409 as expected** responses                                        | k6's default (every 4xx is a failure)             | 409 SEAT_UNAVAILABLE is the correct answer for 950 of 1,000 spike users; "failed" should mean real failures                         |
| H7  | Scenario B has **no think time**                                                       | Simulated user pauses                             | Worst case for latency; targets met anyway                                                                                          |
| H8  | Spike latency **reported, not asserted**; drain time and throughput reported alongside | Percentiles only                                  | In a simultaneous spike, latency is mostly queueing; drain time explains it                                                         |
| H9  | **No performance changes** made                                                        | Micro-optimising the hold path                    | G7 targets met with large headroom; the spike's limit is one Node process's CPU, addressed by running more instances, not by tuning |
| H10 | **Same-seat requests fired together** (`contendedOrder`) in T1, the spike and the demo | Plain order _i_                                   | With a 20-connection pool, plain order never overlapped two requests for one seat, so the race wasn't really tested                 |
| H11 | The **deliberately broken naive hold lives in `demo/`**, never in `apps/`              | No demo, or a flag in the real API                | Shows the bug and proves the tests can fail, without any risk of shipping it                                                        |
| H12 | Linux verification runs **on the compose network**                                     | Reaching databases through `host.docker.internal` | That forwarding path occasionally dropped new connections under bursts                                                              |

## Known limitations (documented, not bugs)

- **Crash between the pay commit and the gateway call:** the payment stays INITIATED and the gateway never sees it. A same-key retry replays the 202 without calling the gateway. The hold expires, and the sweep fails the payment after 15 minutes.
- **Lost webhook:** the payment stays INITIATED until the sweep (15 min); the checkout UI shows "processing" until then. No gateway polling (PRD non-goal).
- **`now()` is the transaction start time**, so a confirmation can land slightly after nominal expiry by the length of a lock wait. Safe, because seat ownership is re-verified under lock.
- **Role changes** take effect only on the next login (JWT carries the role, 1-hour expiry).
- **Fixed-window rate limiting** allows up to twice the limit across a window boundary.
- **While Redis is down there is no rate limiting at all** (fail open, by design), logged as a warning every 10 s.
- **ioredis keeps a process alive for about 2.3 s after a refused connection** (measured on Windows and Linux). No effect on requests; only relevant to test teardown.
- **The admin retry is per event**; there's no bulk retry.
- **Delivery is at-least-once**, never exactly-once. Both consumers are idempotent (unique `event_id`; the gateway dedupes refunds per payment).
- **A slow-but-alive handler** whose lease expires can overlap with a second worker running the same event. Harmless because consumers are idempotent, and the fencing token keeps only one result.
- **Notification latency** is up to one worker tick (5 s), since the outbox is polled rather than pushed.
- **FAILED outbox events** need a human to fix the cause, then retry them through the admin endpoint.
- **The mock gateway keeps state in memory.** If it restarts, refunds for charges made before the restart fail (unknown payment) and end up FAILED after retries.
- **Local test environment:** on desktop Windows, tests that open hundreds of simultaneous connections need the client socket pool (E4). Linux CI doesn't.
- **One API process tops out at one CPU core.** Under the spike it drained ~250–350 holds per second; more throughput needs more API instances. Correctness doesn't depend on it.
- **Load numbers come from one laptop**, with every container sharing a Docker Desktop VM; run-to-run variance was noticeable (spike p95 2.1–3.0 s). Not a production benchmark.
- **The API runs through `tsx`**, not compiled JavaScript. Only startup differs; it isn't expected to change the steady-state numbers, but it wasn't measured separately.
